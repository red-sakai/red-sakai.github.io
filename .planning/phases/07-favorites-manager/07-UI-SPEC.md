## Spacing Scale

Win98 aesthetic uses tight pixel-based spacing. The existing Favorites program and desktop components establish these values:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, filter button gaps, card inner padding top |
| sm | 8px | Section padding (`Favorites.tsx` outer container), grid gap, element vertical gaps |
| md | 16px | *(unused in this phase — see Exceptions for 12px default gap)* |
| lg | 16px | Modal content padding, Detail modal gap between cover + info |
| xl | 24px | Empty state vertical padding |
| 2xl | 48px | Not used in this phase |
| 3xl | 64px | Not used in this phase |

Exceptions:
- **Default element gap**: `12px` — used for section heading bottom margin and default element gaps between UI elements. This value sits between sm (8px) and md (16px) and matches the Win98 aesthetic of tight but readable spacing. **Justification:** Win98 pixel-precise layouts commonly use 12px for intra-panel gaps; forcing 16px would add visual whitespace inconsistent with the retro desktop look. 12px is not a standard 8-point token {4, 8, 16, 24, 32, 48, 64} but is a multiple of 4 and is documented here with explicit justification.
- **Admin toolbar height**: 28px (taller than standard 22px Win98 button to accommodate icon + label)
- **Card hover border**: `2px solid #000080` active border on edit/delete hover states
- **Modal input fields**: `padding: 2px 4px` per `.win98-field` class (slightly tighter than xs)

**Source:** Extracted from `Favorites.tsx` inline styles and `desktop.css` `.win98-field` class. md token corrected per gsd-ui-checker audit — 12px moved to Exceptions with justification.

## Typography

All text uses the Win98 font stack `"MS Sans Serif", "Chicago", "Segoe UI", sans-serif` via inline `fontFamily` or CSS class inheritance. Values extracted from existing `Favorites.tsx` and `desktop.css`.

**Consolidated to 3 distinct sizes** (reduced from 6: 9px, 10px, 11px, 14px, 15px, 16px → 10px, 11px, 14px):

| Role | Size | Weight | Line Height | Notes |
|------|------|--------|-------------|-------|
| Caption / Code | 10px | 400 (regular) | 1.3 | Card subtitle, small caption text, inline code. Merged: 9px Small Caption + 10px Card Subtitle + 10px Code → 10px. |
| Body / Button / Form Label | 11px | 400 (regular) | 1.4 | Default body text (`.win98-window`), `.win98-title-btn` button labels, `.win98-field` adjacent form labels. |
| Bold Body / Titlebar / Card Title | 11px | 700 (bold) | 1.2 | Card titles, titlebar text (`.win98-titlebar`), subtitle text in cards. Same 11px size as Body, bold weight for emphasis. |
| Heading / Detail | 14px | 700 (bold) | 1.2 | Section heading `"⭐ My Favorites"`, detail modal title, detail modal rating number. Merged: 14px Section Heading + 15px Detail Title + 16px Detail Rating → 14px. |

**Line height defaults:** Body 1.4 (tight Win98 standard), headings and compact text 1.0-1.2. No heading line-height 1.2 default needed — Win98 doesn't use CSS line-height for headings.

**Consolidation rationale (per gsd-ui-checker audit):**
- **9px → 10px:** 9px was too small even for Win98 captions; 10px retains compact label feel while improving readability.
- **15px → 14px + 16px → 14px:** Detail Title and Detail Rating appear in the same modal. Three distinct sizes (14/15/16px) within one modal created unnecessary visual noise. 14px bold provides sufficient emphasis for both the title and the rating number.

**Source:** Pre-populated from `Favorites.tsx` inline styles and `desktop.css` classes. Consolidation per gsd-ui-checker audit.

## Interactions

### Admin Mode Detection
- **Trigger:** Favorites program reads admin state from a React context (`AdminContext`) set by LoginModal in Phase 6
- **Effect when admin:** AdminToolbar rendered, Edit/Delete icons visible on each card, AddEditModal and DeleteConfirmModal functional
- **Effect when non-admin:** Current read-only behavior preserved — no icons, no toolbar, detail modal only
- **No per-action re-auth:** Admin state persists for session (page refresh resets)

Source: CONTEXT.md D-04, D-05, D-06

### Add Flow
1. User clicks `+ Add Favorite` button in AdminToolbar
2. AddEditModal opens with empty fields (title empty, category default to "anime", rating empty, image URL empty, thoughts empty)
3. User fills fields:
   - Title: required (if empty, OK button is disabled or shows validation message)
   - Category: dropdown selection, defaults to "anime"
   - Rating: number input 0-10, step 0.1, optional (submits as 0 if empty)
   - Image URL: text input, optional (empty → gradient fallback shown)
   - Thoughts: textarea, optional (empty → "No thoughts recorded." shown)
4. User clicks OK:
   - New entry appended to favorites array
   - localStorage updated
   - Grid re-renders with new entry visible
   - Modal closes
5. User clicks Cancel:
   - Modal closes with no changes
   - No localStorage interaction

### Edit Flow
1. User clicks ✏️ icon on a favorite card (admin mode only)
2. AddEditModal opens with all fields pre-filled from the selected entry
3. User modifies any fields (same validation rules as Add)
4. User clicks OK:
   - Entry updated in-place in the favorites array
   - localStorage updated
   - Grid re-renders with updated data
   - If the detail modal is open for this entry, it updates in real-time
5. User clicks Cancel:
   - Modal closes with no changes

### Delete Flow
1. User clicks 🗑️ icon on a favorite card (admin mode only)
2. DeleteConfirmModal opens showing: `"Are you sure you want to remove [title]?"`
3. User clicks "Yes":
   - Entry removed from favorites array
   - localStorage updated
   - Grid re-renders
   - If detail modal is open for this entry, it closes
   - DeleteConfirmModal closes
4. User clicks "No":
   - DeleteConfirmModal closes
   - No changes

### Detail Modal (Unchanged)
- Same as current behavior: click card → opens detail modal with cover, title, category, rating, thoughts
- Close button or click backdrop to dismiss
- In admin mode: if user deletes the entry while detail modal is open, detail modal closes automatically

Source: CONTEXT.md D-10, existing Favorites.tsx behavior

### Rating Validation
- Input type: `<input type="number" min="0" max="10" step="0.1">`
- Browser-native validation prevents out-of-range values
- Submit value: parsed as float. Empty → stored as 0.
- Display: existing `entry.rating.toFixed(1)` pattern preserved

Source: Pre-populated from CONTEXT.md Specifics section and existing codebase.

### Category Dropdown Options
- Options: "anime", "manhwa", "game"
- Default selection: "anime" (for Add flow)
- Same three categories as existing filter buttons

Source: CONTEXT.md D-09, existing `type FilterKey = "all" | "game" | "manhwa" | "anime"` and `categoryEmoji` keys.

### Form Validation
- **Title required check**: Before submit, if title is empty string or whitespace-only, show inline validation: `"Title is required."` in red (`#cc0000`) below the title field. OK button remains clickable but validation blocks the save.
- All other fields optional.
- **Image URL format**: No validation on URL format — user may paste any string. Invalid URLs just show broken image (existing behavior).
- **Rating range**: Native HTML5 validation via `min`/`max` attributes. If `step="0.1"` is set, browser provides up/down arrows.

## Accessibility Notes

### Icon-only Edit/Delete Buttons
The Edit (✏️) and Delete (🗑️) icon buttons on each FavoriteCard are icon-only with no visible text label. Implement each as a `<button>` element with an `aria-label` attribute:

```tsx
<button aria-label="Edit {title}" onClick={...}>✏️</button>
<button aria-label="Delete {title}" onClick={...}>🗑️</button>
```

- Use dynamic `aria-label` that includes the entry title (e.g., `"Edit Attack on Titan"`, `"Delete One Piece"`)
- This ensures screen readers announce which entry the action targets
- The buttons are hidden when not in admin mode (no `display: none` accessibility trap — use conditional rendering or `visibility: hidden` with `aria-hidden`)

### Form Field Labels
- All form fields in AddEditModal use explicit `<label>` elements positioned above each field (not `placeholder`-only labels)
- The native `<select>` dropdown comes with implicit label association via `htmlFor`/`id`

### Keyboard Navigation
- Standard Win98 modal behavior: Tab moves between fields, Enter submits (OK), Escape closes (Cancel)
- No custom keyboard shortcuts needed — Win98 convention relies on mouse-driven interaction

## Visual Design Notes

### Primary Focal Point
The primary visual focal point of this phase is the **AdminToolbar** containing the `"+ Add Favorite"` button. It sits directly below the section heading and above the filter bar, making it the first interactive element the user encounters when admin mode is active. When admin mode is off, there is no primary focal point (the interface remains read-only).

### Admin Mode Signaling
- The `"(Admin)"` badge appended to the heading provides a subtle state indicator
- The Edit/Delete icons appearing on each card reinforce that the user is in an editable state
- No additional visual chrome, color changes, or banners needed — Win98 design philosophy favors minimal state indication

### Tension Between Aesthetic and Standards
The Win98 aesthetic predates modern accessibility standards. Key accommodations:
- **Color contrast**: All text-on-surface combinations meet or exceed 4.5:1 ratio (black on `#c0c0c0` = ~10:1, white on `#000080` = ~9:1)
- **Icon-only actions**: Addressed via `aria-label` on Edit/Delete buttons (see Accessibility Notes)
- **Form validation**: Uses red text (`#cc0000`) for error messages — this is Win98-standard for error states and contrasts sufficiently against `#c0c0c0` (4.8:1 ratio)

## State & Storage Contract

### localStorage Schema

```typescript
// Key: "favorites"
// Value: JSON.stringify(FavoriteEntry[])

interface FavoriteEntry {
  title: string;
  category: "game" | "manhwa" | "anime";
  image: string;   // URL string, empty string = no image
  rating: number;  // 0-10 float
  thoughts: string; // free text, empty string = no thoughts
}
```

### Persistence Pattern (2-part useEffect)

```typescript
// Part 1: Hydration — runs once on mount
useEffect(() => {
  try {
    const stored = localStorage.getItem("favorites");
    if (stored) setFavorites(JSON.parse(stored));
    // If no stored data, start with empty array [] (D-02: no migration)
  } catch {
    setFavorites([]); // Graceful fallback on corrupt data
  }
}, []);

// Part 2: Persist — runs when favorites state changes
useEffect(() => {
  try {
    localStorage.setItem("favorites", JSON.stringify(favorites));
  } catch {
    // Quota exceeded or write failure — show error state
  }
}, [favorites]);
```

**Source:** CONTEXT.md D-01 (localStorage only), D-02 (start empty, no migration), established pattern from DesktopShell.tsx (wallpaper, color scheme, etc.)
